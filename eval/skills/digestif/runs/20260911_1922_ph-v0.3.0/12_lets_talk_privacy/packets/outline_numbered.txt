L002:     Summary: Encrypted chats still trust providers; only client-held keys minimize that trust. (¶2, ¶18, ¶27)
L003:         - 1 E2EE means device-to-device secrecy, but users need provider exclusion, not just transit safety. (¶1, ¶2)
L004:             - 1.1 Nuance: Non-expert end-user inquiry from a conversation with Omid. (¶1)
L005:             - 1.2 Nuance: Metadata (network, frequency, volume, timing) still aids interpretation. (¶2)
L006:             - 1.3 If claims hold with no backdoors, Meta cannot read; closed source blocks certainty. (¶3)
L007:             - 1.4 Business model, 2021 ad-sharing policy, and 2019 plaintext failure imply near-certain access. (¶3)
L008:         - 2 Smoking gun: history on a new device with no manual key transfer. (¶4)
L009:             - 2.1 Example: Locker plus receiver-only master key; server key touch equals public billboard copy. (¶4)
L010:             - 2.2 WhatsApp server stores encrypted history and hands keys to devices it authenticates. (¶5)
L011:             - 2.3 Nuance: Device lists and codes rely on honest reporting; a rogue device could hide. (¶5)
L012:         - 3 Proton generates the private key in-browser, wrapping it with bcrypt and AES-256. (¶6)
L013:             - 3.1 Evidence: Six-step login: type, bcrypt with server salt, authenticate, fetch key, decrypt locally, read. (¶7)
L014:             - 3.2 Hashing authenticates one-way; encryption protects two-way under the actual password. (¶8)
L015:             - 3.3 Nuance: In theory the seen hash cannot decrypt the password-wrapped key. (¶9)
L016:         - 4 Counterpoint: Malicious client code could capture the typed password before hashing. (¶10)
L017:             - 4.1 Nuance: Trust needs matching code, no compelled injection, uncompromised infrastructure. (¶10)
L018:             - 4.2 Proton must steal the password first; WhatsApp grants keys directly. (¶11)
L019:         - 5 Signal: 30-digit passphrase file, device-to-device transfer, or unseen 64-character key. (¶12)
L020:             - 5.1 Evidence: Android backup needs physical transfer; direct transfer needs both devices present. (¶12)
L021:             - 5.2 Nuance: Zero-knowledge: no decryption, no recovery help after a lost key. (¶13)
L022:         - 6 Plaintext password storage cannot be ruled out with certainty. (¶14, ¶20)
L023:             - 6.1 Open clients prove sending behavior, never the server's later handling. (¶15)
L024:             - 6.2 Evidence: Facebook logged hundreds of millions plaintext for years; Adobe leaked hints; MD5 persists. (¶16)
L025:         - 7 Evidence: Proton reset destroys old mail, suggesting genuine inability, but proves nothing. (¶17)
L026:             - 7.1 Trust rests on reputation, jurisdiction, model, behavior, not verifiable guarantees. (¶18)
L027:             - 7.2 Escrow (WhatsApp) versus password-wrapped (Proton) versus client-controlled (Signal). (¶19)
L028:             - 7.3 Evidence: Rogue device: YES for WhatsApp; NO for Proton and Signal (client caveat). (¶19)
L029:         - 8 Checkable: open clients, Wireshark traffic, audits of deployed code. (¶21)
L030:             - 8.1 Uncheckable: running code, later updates, rogue staff, breaches. (¶22)
L031:             - 8.2 Evidence: Good: open servers, audits, clean breaches; bad: reset-proof data, obscurity, violations. (¶23)
L032:             - 8.3 Evidence: Facebook 2019: 200-600 million passwords, 20,000+ searchers, archives from 2012. (¶24)
L033:             - 8.4 Trust ends only with client-side crypto, zero-knowledge servers, verifiable builds. (¶25)
L034:             - 8.5 WhatsApp needs whole-infrastructure trust; Proton hashing honesty; Signal key custody. (¶26)
L035:             - 8.6 Prefer client-side encryption, open source, decentralization, hardware keys like YubiKey. (¶27)
L036:         - 9 Evidence: Sources: Meta 2021 engineering, Proton key docs, Signal September 2024 backups. (¶28)
