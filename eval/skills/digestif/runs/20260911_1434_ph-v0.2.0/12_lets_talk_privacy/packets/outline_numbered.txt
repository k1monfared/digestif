L002:     Summary: Encryption excludes providers only when clients hold keys; WhatsApp escrows, Proton needs trust, Signal minimizes. (¶1, ¶2, ¶4, ¶62)
L003:         - 1 End-to-end encryption can mean several practical things beyond device-to-device ciphertext. (¶3, ¶4)
L004:             - 1.1 Nuance: Real goal is excluding the provider, though metadata like contacts and timing still leaks. (¶4)
L005:             - 1.2 Meta likely accesses WhatsApp content given closed source, ad-data sharing, past plaintext failures. (¶5)
L006:         - 2 Smoking gun: history portability without manual key transfer betrays server key access. (¶6, ¶7)
L007:             - 2.1 Nuance: Signal forces manual key copy; any server-touchable key is like public copies. (¶7)
L008:         - 3 WhatsApp server stores encrypted history and maps accounts to device identities. (¶8, ¶9)
L009:             - 3.1 Counterpoint: Server-authenticated new devices receive decryption keys; rogue devices could hide from lists. (¶9)
L010:         - 4 Proton generates browser-side keys, then stores them server-side encrypted under user password. (¶10, ¶11)
L011:             - 4.1 Evidence: Login: bcrypt-hash authenticates, server returns encrypted key, browser decrypts locally. (¶12, ¶13) [reported]
L012:             - 4.2 Nuance: Hashing authenticates one-way while encryption reversibly protects the private key. (¶14, ¶15, ¶16, ¶17)
L013:             - 4.3 Counterpoint: Proton could serve malicious client code capturing passwords, then decrypt stored keys. (¶18)
L014:             - 4.4 Nuance: Open source helps only if served code matches, stays honest, infrastructure stays clean. (¶19)
L015:             - 4.5 Unlike WhatsApp, Proton must first compromise the client to steal passwords. (¶20)
L016:         - 5 Signal stores history on-device, deleting server copies after delivery. (¶21, ¶22)
L017:             - 5.1 Example: Migration needs physical backup plus passphrase, device transfer, or unseen recovery key. (¶23)
L018:             - 5.2 Signal servers cannot grant history access; recovery keys stay client-side and unrecoverable. (¶24)
L019:         - 6 Password handling adds another unverifiable layer beneath encryption architecture. (¶25, ¶26)
L020:             - 6.1 Nuance: Client hashing is verifiable in open source; server behavior after arrival is not. (¶27, ¶28)
L021:             - 6.2 Evidence: Facebook logged hundreds of millions of plaintext passwords; Adobe hints leaked; small services worse. (¶29) [reported]
L022:             - 6.3 Nuance: Proton password-reset data loss suggests honest design but proves nothing about capability. (¶30)
L023:             - 6.4 Without client crypto guarantees, users trust reputation, jurisdiction, model, history. (¶31)
L024:             - 6.5 Architecture sets trust surface: Meta infrastructure, Proton client integrity, Signal key custody. (¶32)
L025:         - 7 Comparison names WhatsApp escrow, Proton password-encrypted storage, Signal client control. (¶33, ¶34, ¶35, ¶36)
L026:         - 8 Nobody can verify that companies avoid plaintext password storage. (¶37, ¶38)
L027:             - 8.1 Evidence: Verifiable: open clients, traffic checks, audits with published results. (¶39, ¶40, ¶41, ¶42)
L028:             - 8.2 Nuance: Unverifiable: closed server code, later changes, rogue staff, breaches. (¶43, ¶44, ¶45, ¶46)
L029:             - 8.3 Nuance: Look for open servers, audits, breach behavior; beware resets, obscurity, violation history. (¶47, ¶48, ¶49, ¶50, ¶51)
L030:             - 8.4 Evidence: Adobe 2013 hints, Facebook 2019 plaintext logging, small services with weak unsalted storage. (¶52, ¶53, ¶54, ¶55)
L031:             - 8.5 Trust-minimizing needs client-side crypto, zero-knowledge servers, reproducible audited builds. (¶56, ¶57, ¶58)
L032:             - 8.6 Evidence: Applied trust: WhatsApp everything, Proton hashing plus client, Signal implementation plus custody. (¶59, ¶60, ¶61)
